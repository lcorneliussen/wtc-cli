# wtc 0.1.61

This release adds operator-controlled project discovery for OpenClaw sandboxes,
clearer service and pull-request status, persistent tunnel choices, and safer
review audience selection. It also brings the taba wordmark to the OpenClaw
interface and prepares more configuration and state readers for the future
rename. The shipped executable and release archives remain named `wtc`.

## Collections

- **Retirement stops native and relatively launched status watchers.** Live views register with their resolved collection and stop before its worktrees are removed. Legacy shell watchers are matched by verified collection scope and process identity; unrelated commands and stale registrations are left safe. Both `wtc` and `taba` invocations are supported ([#120](https://github.com/lcorneliussen/wtc-cli/issues/120)).

- Add `wtc open --add review` for pinned review bundle or current PR diffs, using Hunk when available and Git/less otherwise.
- Preserve review viewers across layout switches and keep focused or running review panes during trimming; default and full pane sets remain unchanged.

## Services

- **Tunnel exposure is named in status.** Public addresses show `[public]`, and their color follows service health. Running tunnels with unknown exposure are labeled explicitly and remain warning-colored; plain service output names exposure too. The runtime-status contract now has end-to-end wiring coverage for live reachability and provider-login observations, while startup polling keeps its runner-only view ([#157](https://github.com/lcorneliussen/wtc-cli/issues/157), [#172](https://github.com/lcorneliussen/wtc-cli/issues/172)).

- Service `down` preserves explicit tunnel on/off intent; `up` and `restart` restore enabled tunnels after provider checks. `wtc svc tunnel --stop` keeps them off, overriding declaration defaults.
- Choices are collection-local and bound to the approved definition. Changed or removed declarations need a fresh choice before reopening; public tunnels still require explicit approval.
- Status reports intended-on tunnels that are not running separately from login, reachability and exposure diagnostics.

- **Changed runtime tasks reach the live runner.** Configuration updates use dekit's native reload before restarting changed running tasks. Newly added tasks become available, removed tasks are stopped, and changes made while down replace the saved definitions on the next start. An already-stale runner can import its generated configuration with `wtc svc dekit -- reload --yes` ([#208](https://github.com/lcorneliussen/wtc-cli/issues/208)).

## OpenClaw

- **Sandbox sessions discover operator-allowed gateway projects.** Project names and repository branches can be resolved through the sandbox Git service. Plans needing new gateway base records, worker inheritance or another collection are directed to the gateway collection session. Discovery is denied by default, with an explicit per-agent allowlist, and grants no additional Git, clone or publication access. See [project discovery in a sandbox](https://github.com/lcorneliussen/wtc-cli/blob/main/docs/sandbox-projects.md) for operator setup ([#171](https://github.com/lcorneliussen/wtc-cli/issues/171)).

- **The plugin's visible branding is now taba.** The card and Collection panel use the selectable “束 taba” wordmark and link to taba.sh; plugin metadata says “taba,” with “Formerly wtc” in its description. Existing plugin/package IDs, configuration, action routing and CLI/skill names stay compatible. Upgrade the CLI and matching plugin with `wtc openclaw install`, then reload Control UI tabs. The technical identity migration remains a later part of [the rename plan](https://github.com/lcorneliussen/wtc-cli/issues/200).

- **The taba Collection wordmark shares one text baseline.** The logo stays centered while “taba” aligns with “Collection” in both the composer card and side panel. The selectable Unicode wordmark, product link and technical plugin identity stay the same.

- **Clearer commit and publication results.** The OpenClaw card and panel
  distinguish saving local commits, pushing commits to an existing pull request,
  and creating a draft pull request. Bitbucket no longer offers an empty push
  when files still need committing. After publication, Review PR text asks the
  conversation to compare the title and description with the complete current
  PR diff and propose revisions; it does not edit remote text or request a code
  review.

## Rename preparation

- **PR and status readers accept taba filenames.** PR enlistments read `.taba-prs` when `.wtc-prs` is absent; cached status accepts `.taba-status.json` and `.last-taba-status.yml` under the same legacy-first rule. PR mutations carry the selected registry into the legacy output under the existing shared lock, preserving rows and merge facts. Status refreshes and default catch-up reports keep legacy output names. Retirement also removes the corresponding alternate report/cache files. No automatic migration or runtime-identity change is included. See [collection-state compatibility](https://github.com/lcorneliussen/wtc-cli/blob/main/docs/rename-collection-state.md) and [phase 0](https://github.com/lcorneliussen/wtc-cli/issues/201).

- **Accept alternate configuration input names.** `taba.toml`, `.taba-version`, `taba.env`, existing XDG `taba` directories, `SCOPE.md`, and `.taba-base.sha256` are accepted. Existing legacy paths remain authoritative; fresh output keeps legacy names. `wtc upgrade` edits the selected pin/config filenames in place and checks those files for uncommitted changes. No automatic migration or runtime-state namespace change is performed. See [configuration inputs](https://github.com/lcorneliussen/wtc-cli/blob/main/docs/rename-config-inputs.md) for precedence and scope ([#201](https://github.com/lcorneliussen/wtc-cli/issues/201)).

- **Help and command hints follow the invoked name.** Invoking the executable as `taba` selects that name for command paths, examples, diagnostic prefixes and authored command hints; `wtc` keeps its current spelling. Dev-build handover preserves the invocation. File paths, environment variables, plugin/skill IDs, protocol markers and executable packaging remain unchanged; no rename notice is added. See [invocation-aware command names](https://github.com/lcorneliussen/wtc-cli/blob/main/docs/rename-invocation.md) ([#201](https://github.com/lcorneliussen/wtc-cli/issues/201)).

## Status

- **Status shares one Bitbucket and GitHub allowance.** Build lookups are cached with pull requests. One fetch serves every status pane asking for that record, and an identical response refreshes that entry's age. Bitbucket then allows a short burst and about one call every 8 seconds; GitHub allows a larger burst and about one call every 2 seconds. A rate-limit response pauses that forge and status keeps the last saved record. A call that waits because the allowance is spent stays blank instead of showing an error ([#215](https://github.com/lcorneliussen/wtc-cli/issues/215)).
- **Status compares the open list before it fetches a pull request.** Bitbucket's list carries `updated_on`, comment count, task count, and review markers. GitHub's list carries `updatedAt`, the review decision, and check conclusions. A matching stamp keeps the saved detail. A changed stamp is applied from the list. The full pull request is fetched when it leaves a list that was read to the end. A full GitHub list still gets one query for a branch that was not on it. One recent Bitbucket pipeline page answers for every branch on that page, and each of those runs is saved. A branch that has never appeared gets its own lookup. A missing pipelines endpoint is remembered as no builds, and a failed response keeps a short excerpt of the body.
- **Status still reads the full record about every 10 minutes.** The list comparison runs first. The full read then runs, and any field it disagrees with is appended to `incremental-misses.log` in the status cache and shown in the refresh log. `WTC_FORGE_FULL_REFRESH` is that interval in seconds; `0` turns it off. A saved Bitbucket build gets the same check against that branch's own pipeline query.
- **Status reads Bitbucket pull request lists through the REST API.** The open list and branch discovery no longer call `bb pr list`. They use the same credentials as pipeline lookups: the `bb` login, or `BB_USERNAME` and `BB_API_TOKEN`.

- **Bitbucket PR conflicts are visible before starting a merge.** When the reported source and destination commits are available locally, status predicts the merge without changing the checkout and shows confirmed conflicts in the repository and PR rows. JSON records the commit pair and conflicting paths. Unavailable predictions stay unknown ([#217](https://github.com/lcorneliussen/wtc-cli/issues/217)).

## Review

- **Local reviews surface scope and design checkpoints.** Reports flag patch growth above 50% since the last completed compatible round and ask a design question when major findings persist in the same concern at round 3 or later. Review guidance now asks for whole-invariant fixes, deterministic race evidence and compact carry-over, while preserving the existing review gate and audience isolation ([#220](https://github.com/lcorneliussen/wtc-cli/issues/220)).

- **Intentional behavior can still need a clearer explanation.** Review guidance distinguishes behavior changes from valid wording, diagnostic and comment clarifications; optional style advice has no gate significance. Reviewers reread current supplied evidence before repeating a stale pending-test claim ([#220](https://github.com/lcorneliussen/wtc-cli/issues/220)).

## Review privacy

- Review bundles now default to public mode for public or unknown visibility,
  different forge namespaces, or an unknown harness namespace. Confirmed private
  targets in the harness namespace retain private mode; `--private` explicitly
  opts into harness context, while `--public` forces isolation.
- Public bundles use target base-commit concerns under `review/concerns/` and
  `.review/concerns/`, or embedded defaults, with embedded prompts. They exclude
  harness overlays, related patches, repository snapshots, and private rounds.
- Bundle output, manifests, and progress/verdict comments expose the selected
  mode. Private bundles require fresh private visibility before posting or
  resolving, including progress/failure posts; `--force` cannot bypass this.
- Harness adoption: update overridden local-review skills to use automatic
  selection and inspect the mode. Rebuild and rerun old private bundles with
  `--public` before publishing to public or unknown audiences. See
  [review audience rules](https://github.com/lcorneliussen/wtc-cli/blob/main/docs/review-audiences.md) for the exact contract and limitations.


## Compatibility and adoption

- Update the harness CLI pin and compatibility range together. Read the complete
  upgrade range, preserve project policy and overlays, then run `wtc env setup`,
  `mise install`, `wtc skills render`, and `wtc mcp render`. Compare overridden
  skills with the shipped defaults, especially review audience selection,
  current-evidence review guidance, and alternate scope-file selection.
- Existing `wtc` filenames take precedence over alternate taba filenames. There
  is no need to rename files now, and no automatic migration. Fresh generated
  output, environment/protocol identities, runtime namespaces, and technical
  plugin and skill IDs keep their existing spellings. Invocation-aware help
  does not add a packaged `taba` executable.
- For OpenClaw, run `wtc openclaw install` to install the matching plugin and
  reload Control UI tabs. Sandbox project discovery requires compatible wtc
  versions on both gateway and sandbox, the sandbox Git service connection,
  and an explicit gateway-side `sandboxGit.projectsByAgent` allowlist. An
  allowed project exposes its registry metadata to every sandbox session of
  that agent; choose separate agents when metadata visibility must differ.

## Limitations

- Sandbox discovery stays default-deny and grants no additional repository
  read, clone, worktree, or publication permission. Plans requiring new gateway
  base records, worker inheritance, or another collection must be prepared in
  the gateway collection session.
- Public review mode isolates bundle inputs; it does not sanitize target PR
  text or generated reports. Inspect the exact bundle before review and the
  exact summary, inline comments, and replies before public posting.
- Bitbucket conflict prediction needs both reported commits locally; missing
  evidence remains unknown. Forge throttling can leave a saved record visible
  or a pending lookup blank until the allowance is available.
