# wtc 0.1.50

On an OpenClaw gateway, a harness is now a **wtc project**: a named set of
repositories, with `wtc projects` to list them. The agent starts a collection
whenever someone wants to work on a repository. The agent's pull request text
reaches the pull request, and the conversation hears when a pull request
opens, fails its checks, gets a review or merges. A conversation without a
collection says so, and the panel shows which build the gateway runs.
Sandboxed sessions can catch up in their sandbox.

## OpenClaw: sandboxes

- **A sandboxed session catches up in its sandbox, and its commits reach the
gateway.** With the plugin's new git service (`sandboxGit` in the plugin's
config, `WTC_GATEWAY_GIT` in the sandboxes' environment), the sandbox reads
the gateway's clones, read-only and with history, and `wtc catch-up` merges
the base there with Git's own conflict state; `wtc catch-up --continue`
finishes a resolved merge. The gateway then takes the session's branch, the
sandbox's commits included, once it has checked that the branch extends its
own, merges only origin's commits and leaves no conflict markers. The service
answers only the gateway's sandbox containers, tells them apart by their
address, serves each only its collection's branches and origin's, refuses
pushes and hands out no forge credential. In a sandbox, `wtc doctor` checks
the service and fails when a credential that could push is present
([#113](https://github.com/lcorneliussen/wtc-cli/issues/113)).

## OpenClaw: pull requests

- **The agent's title and description reach the pull request.** `wtc publish`
  takes `--title` and `--body` or the new `--body-file`, and records them for
  the branch in the worktree's git directory, never committed. `wtc status
  --json` reports them as `proposal`. The card's ↑ opens the pull request with
  them and shows the title before you push. Without one, the pull request
  still opens as "Publish openclaw/<name>". Bitbucket's publish takes the
  title only
  ([#141](https://github.com/lcorneliussen/wtc-cli/issues/141)).
- **The conversation hears what happened to its pull requests.** It's told
  when one opens or becomes ready, is merged or closed, fails or passes its
  checks, is approved, gets a request for changes, or conflicts with its
  base, with a turn of its own. The plugin looks whenever a card loads, and
  every 5 minutes at collections with an open pull request. The new plugin
  settings `pullRequestEvents` (`wake`, `queue`, `off`) and
  `pullRequestPollMinutes` change that. GitHub only
  ([#141](https://github.com/lcorneliussen/wtc-cli/issues/141)).
- **After a merge, the card offers the catch-up.** A merged pull request whose
  merge the checkout doesn't have yet shows ↓, which fetches the base and
  merges it in. `wtc status` reports this as the pull request's `mergedIn`
  ([#144](https://github.com/lcorneliussen/wtc-cli/issues/144)).
- **The conversation acts on pull request news.** The event now asks the
  agent to bring the task's progress up to date, to catch up after a merge,
  and to tell the person only what they need to act on
  ([#144](https://github.com/lcorneliussen/wtc-cli/issues/144)).

## OpenClaw: the Collection panel

- **A conversation without a collection says so.** Its panel no longer shows
  the conversation's label, "0 repositories" or "null". It explains what a
  collection is and offers to add a repository. A new conversation no longer
  shows its parent's collection
  ([#146](https://github.com/lcorneliussen/wtc-cli/issues/146)).
- **The panel shows which build the gateway runs.** Its footer and the card's
  wtc tooltip name the plugin's and the gateway's wtc versions. A build
  without a release version describes itself much like `wtc dev install` does,
  e.g. `0.1.50-dev+g<commit>.<yyyymmdd.hhmm>.dirty`, and stamps the plugin with
  it ([#146](https://github.com/lcorneliussen/wtc-cli/issues/146)).

## OpenClaw: wtc projects

- **A harness is a wtc project.** The skill, the instructions, the docs,
  `wtc add-repo`'s questions and `wtc status` now call a configured
  harness a wtc project: a named set of repositories, whose collections are
  one task's worktrees of them. The panel names a collection's project, or
  "ad-hoc wtc project". The config keys and the folders stay as they are
  ([#148](https://github.com/lcorneliussen/wtc-cli/issues/148)).
- **`wtc projects`** lists the gateway's wtc projects with their
  repositories and roles. `wtc add-repo --project` is `--harness` under
  its new name, and the old one still works
  ([#148](https://github.com/lcorneliussen/wtc-cli/issues/148)).
- **Every task starts a collection.** The agent starts one whenever the
  person wants to work on a repository, also only to read or analyze it. It
  matches what they named with `wtc projects`, and adds the other
  repositories the project's AGENTS.md names for the task
  ([#148](https://github.com/lcorneliussen/wtc-cli/issues/148)).
- **Another project's repository suggests its own conversation.** When the
  collection's wtc project doesn't list a repository and another configured
  project does, `wtc add-repo` adds a fourth choice: work on it in a new
  conversation for that project. Projects stay apart: a collection never
  reads from another project's repositories unless they were added ad hoc
  ([#148](https://github.com/lcorneliussen/wtc-cli/issues/148)).

## Upgrade

- **OpenClaw gateways:** install the new `wtc`, then run `wtc openclaw
  install` so that the gateway's plugin and the agent's `wtc` skill match it.
  Reload open Control UI tabs for the new card and panel.
- **Pull request news** wakes a collection's conversation by default. Set the
  plugin's `pullRequestEvents` to `queue` or `off` for less, and
  `pullRequestPollMinutes` to `0` to look only when a card loads.
- **wtc projects:** nothing to change. `harnesses` and `defaultHarness` stay
  the config keys, `--harness` still works beside `--project`, and the
  collection folders stay where they are.
- **Sandboxes** catch up in place only with the plugin's `sandboxGit`
  configured; without it, nothing changes.
