# wtc 0.1.42

This release lets a team run collections on an OpenClaw gateway: one task,
several repositories, driven from one conversation, with the collection in
the Control UI ([#72](https://github.com/lcorneliussen/wtc-cli/issues/72)).
See `docs/openclaw.md`. Behaviour in a terminal and under herdr is unchanged.

## Install on a gateway

- `wtc openclaw install`, run on the gateway's host, installs the OpenClaw
  plugin embedded in this binary, so plugin and `wtc` always match. Run it
  again after upgrading `wtc`. `--dir` only writes the plugin
  ([#93](https://github.com/lcorneliussen/wtc-cli/issues/93)).
- The plugin gives agents a `wtc` skill that points them at
  `wtc docs instructions/openclaw.md`.
- `docs/openclaw.md` walks through the install: `wtc` on the PATH, Git 2.42
  and `gh`, the plugin, optionally openclaw-bitbucket, and what each person
  connects.

## wtc under OpenClaw

- Under an OpenClaw gateway `wtc` plans instead of acting. `wtc host` reports
  the host. `wtc add-repo` prints `sessions_spawn` intents. The new
  `wtc publish` checks a session's managed worktree and prints the intent
  that publishes it. `wtc catch-up` merges without rebasing or pushing.
- A collection is driven from one conversation. Each repository's worktree is
  held by a hidden owner session. `wtc status` keeps one folder per collection
  with a link to each worktree, where `wtc svc` runs its services. Under the
  gateway it fetches each clone's base branch at most every five minutes, so
  "behind" is current. `wtc init` and `wtc new` refuse there.
- `wtc add-repo` takes GitHub and Bitbucket URLs. The gateway clones GitHub
  repositories itself; a Bitbucket one is added in the Control UI first.
- Publishing is the person's. The instructions, the `wtc-pr` skills and
  `wtc publish` tell the agent to say when work is ready to push, and to
  publish itself only when asked. `wtc checkouts` prints the status of
  checkouts as JSON.

## The collection in the Control UI

- A card above the message box is laid out as `wtc status`'s tables. It
  shows:
  - each repository's branch, what is not pushed, and what is behind;
  - pull requests with their CI, conflict and review state;
  - services and their tunnels.
- Actions sit on the facts they change:
  - ↑ pushes;
  - ↓ catches up;
  - a conflict asks the conversation to resolve it;
  - services start, stop and restart one by one or all at once;
  - tunnels open and close with `wtc svc tunnel`.

  A new tunnel can also be the gateway's own OpenClaw portal, offered last
  as "needs ingress" when the gateway has no portal ingress. Under 520 pixels
  every row wraps into two lines.
- A Collection panel has the same tables, the pull requests, and adding
  repositories from the gateway, GitHub or the person's Bitbucket
  workspaces.
- Pushing goes through the gateway, with the person's own GitHub connection
  and only after they confirm; the card says how to connect one. Bitbucket
  repositories are pushed the same way, with the person's Bitbucket login,
  by openclaw-bitbucket 0.3.0 or later.

## Other changes

- `wtc svc tunnel <service> tailscale --public` now says that Tailscale
  tunnels are tailnet-only, and names cloudflare, ngrok and devtunnel for a
  public link.

## Harness upgrade

Nothing in this release needs a harness change. Read
`wtc release-notes --since <old-pin>` with this binary before changing a
harness pin, and update the pin and compatibility range together.
