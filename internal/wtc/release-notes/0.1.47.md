# wtc 0.1.47

This release lets an OpenClaw gateway work in harnesses. A gateway set up for
a team or a task, often by CI/CD, can name the harness repositories its
collections belong to, and collections there resolve repositories, default
branches and instructions through their harness, as a herdr collection does
([#100](https://github.com/lcorneliussen/wtc-cli/issues/100), [#112](https://github.com/lcorneliussen/wtc-cli/pull/112)).

## OpenClaw: harnesses

- **Configuration.** List the harnesses under
  `plugins.entries.wtc.config.harnesses`, each with a `name`, a GitHub or
  Bitbucket `remote` and a `ref` (default `main`), and optionally a
  `defaultHarness`:

  ```json
  "wtc": { "config": {
    "harnesses": [{ "name": "platform", "remote": "https://github.com/example-org/platform-harness.git" }],
    "defaultHarness": "platform"
  } }
  ```

  Each harness must also be a project on the gateway: **Add repository** in
  the Collection panel, or the gateway's own project settings. Without
  harnesses configured, collections are ad hoc as before.
- **A collection works in one harness.** Its first `wtc add-repo` adds a
  managed worktree of the harness on the collection's branch, beside the
  repositories, so a task can change the harness and publish that like any
  other repository.
- **Names resolve through it.** `wtc add-repo api` takes `api`'s remote and
  `default_ref` from the harness's `.harness-repos.yml`. That file is read
  from the collection's worktree of the harness once there is one, and before
  that from the gateway's clone at `ref`. `--base` still wins. A URL or
  `owner/name` that the registry lists gets its `default_ref`; one it does
  not list is added ad hoc.
- **Which harness.** A collection keeps the harness it started with. A new
  one takes `--harness <name>`, else `defaultHarness`, else the only
  configured harness, else the only one whose registry lists every
  repository named. When none of that settles it, `wtc add-repo` tells the
  agent to ask the person. `--harness none` starts a collection without one.
  A different `--harness` for an existing collection is refused: work in
  another harness is another collection.
- **Instructions.** `wtc status` shows the collection's harness and where its
  worktree is, so the agent reads the harness's `AGENTS.md`. The agent
  instructions (`wtc docs instructions/openclaw.md`), the plugin's `wtc` skill
  and `wtc docs setup.md` describe the harness workflow.
- **`wtc doctor`** checks that the harness config is valid, which is
  required, and that each harness is a project on the gateway.
- **Failures stop early.** If the openclaw CLI is there but the gateway's
  config cannot be read, `add-repo` stops with the error rather than going on
  without a harness. A plan that cannot be carried out records no harness for
  the collection. An invalid `--worktree` name is refused before anything is
  written.
- **Not yet.** A harness's hooks, secret links and mise pins do not run on a
  gateway, and herdr layouts do not apply. Several harnesses stacked in one
  collection are tracked in #100. The Collection panel shows the harness
  worktree as an ordinary repository row.

## Collections

- A folder's own `.wtc/config` now decides that it is an ad-hoc collection,
  before `harness/` is looked at, so the name of a linked repository cannot
  change what the folder is. `wtc init` never creates that config inside a
  harness collection, so herdr collections are unaffected. A gateway's
  collection folder that links a repository called `harness` stays the
  gateway's collection.

## Upgrade

The plugin's config schema has the new keys, so a gateway accepts `harnesses`
only with this version's plugin: `wtc openclaw install` after installing
the binary, or a new image with `WTC_VERSION=0.1.47`.
