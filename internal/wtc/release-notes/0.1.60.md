# wtc 0.1.60

This release makes the next repository action visible and usable in terminal
status and OpenClaw, and returns completed GitHub branches to the base tip.

## Next actions

- The terminal table, live status view, OpenClaw card and Collection panel
  show each repository's next action, reason, actor and required approval.
  Press `n` in the live view, select with the arrow keys, and press Enter.
- Catch-up steps needing no approval run for the selected repository only,
  after status is read again. A newly dirty checkout, or a working, blocked
  or unreadable local owner, stays with its agent. Stale selections are
  rejected, and catch-up execution is guarded against overlapping requests.
- Steps needing judgment use the named agent skill. The terminal sends the
  instruction to the collection's idle herdr agent, or displays it to give
  the agent yourself. Approved pull requests open for the person to merge.
- **Commit changes** asks the OpenClaw conversation to review and commit
  pending files. Push retains the existing personal-account confirmation.
  The collapsed card points to actions and pending commits; the expanded
  card shows the latest result in full. Publication refusals are errors
  even when the gateway returns only a status and message.

## Status and completed branches

- `wtc status --json` includes a per-repository `next` field describing the
  next step, who performs it (`by`), whose agreement it needs (`approve`),
  its skill, command or gateway action, and a fact key for deduplication.
  Local catch-up commands select their collection and repository explicitly.
- Status predicts merge conflicts without changing the checkout. Conflicts,
  failed checks and requested changes ask for agent judgment; a clean merge
  into a live branch still requires the agent's agreement. Review-only
  checkouts receive no authoring steps.
- Gateway catch-up returns a completed GitHub branch to its detached base
  tip, including a branch already advanced by an earlier catch-up. Its PR
  leaves the repository row and remains in the pull request list. Follow-up
  commits require a new branch and are kept with their owner.
- When `production_ref` and `release_ref` are empty, a branch that deploys
  itself is shown as PROD using its development ref, except `dev`, whose
  production ref is `master`. A different production ref keeps development
  as TEST. ([#166](https://github.com/lcorneliussen/wtc-cli/issues/166))

## Rename preparation

- **Product settings accept the `TABA_` prefix alongside `WTC_`.** The new spelling wins within a source, including an explicit empty value; environment settings retain precedence over workspace-file defaults. Conflicting values produce one stderr warning per setting without printing values or disturbing JSON output. The matching OpenClaw plugin also accepts `TABA_DECISIONS_OPENAI_API_KEY`. Generated variables, file names, commands, and internal/test/development transport names keep their existing spellings in this increment. See [the compatibility guide](https://github.com/lcorneliussen/wtc-cli/blob/v0.1.60/docs/rename-compatibility.md) and [phase 0](https://github.com/lcorneliussen/wtc-cli/issues/201).

## Adoption and limits

- Upgrade the CLI and, on a gateway, run `wtc openclaw install` to install the
  matching plugin. Reload open Control UI tabs to get the new controls.
- Actions are manual in this release. Refreshing status does not execute
  them automatically; automatic reactions and agent-completion refresh are
  follow-up work under [#179](https://github.com/lcorneliussen/wtc-cli/issues/179).
- Returning to the tip does not rebind an OpenClaw managed owner. Another
  publication round still needs a fresh managed worktree and owner; the
  same-collection path remains [#207](https://github.com/lcorneliussen/wtc-cli/issues/207).
